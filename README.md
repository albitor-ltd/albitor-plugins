# Albitor plugins

The first-party plugin monorepo and marketplace catalogue for
[Albitor Ltd](https://github.com/albitor-ltd)'s
[Claude Code](https://code.claude.com/docs/en/plugins) plugins (albitor-ltd/albitor#3158,
ADR-0090 section 12).

## Install

```bash
claude plugin marketplace add albitor-ltd/albitor-plugins
claude plugin install gds@albitor-plugins
```

## Layout

```text
.claude-plugin/marketplace.json   generated catalogue - never hand-edit
plugins/<name>/                   one directory per first-party plugin
  .claude-plugin/plugin.json      the plugin manifest (name must equal <name>)
catalogue/metadata.json           catalogue-facing description, category, keywords, licence
catalogue/legacy-pins.json        old per-plugin repo and ref, used until the switch-over
catalogue/retired-entries.json    retired entries carried through in legacy mode
scripts/build-catalogue.sh        generates marketplace.json from the tree
scripts/validate-plugins.sh       manifest validation (also run by CI)
```

| Plugin | What it does |
| --- | --- |
| `gds` | GOV.UK Design System and WCAG 2.2 AA accessibility |
| `shadcn` | shadcn/ui on Radix UI and Tailwind CSS |
| `mui` | Material Design (SMUI on SvelteKit, `@mui/material` on React) |
| `carbon` | IBM Carbon Design System for enterprise interfaces |
| `auth` | Cognito-backed sign-up and login |
| `docs` | Diataxis, C4 and arc42 documentation skills |
| `api-go` | The `api-runtime@1` plugin: Go server skeleton, middleware and route slots, paging, local issuer |

The old `visual-*` packs are not migrated; they are retired separately (albitor-ltd/albitor#3176).
`mui` and `gds` are parked for the beta; `docs` stays a skill pack (ADR-0090 section 13).

## Tags and releasing a plugin

Each plugin is released independently with a tag `<name>/vX.Y.Z`, where `X.Y.Z` is the `version` in
`plugins/<name>/.claude-plugin/plugin.json` (for example `auth/v0.7.0`).

1. Change the plugin and bump `version` in its `plugin.json` in the same PR.
2. Merge to `main` once CI is green.
3. Tag the merge commit: `git tag auth/v0.7.0 && git push origin auth/v0.7.0`.
4. In a follow-up PR, regenerate the catalogue (`scripts/build-catalogue.sh --mode monorepo`) so it
   pins the new tag. Only tag-then-regenerate keeps the catalogue from pointing at a tag that does
   not exist yet.

## The catalogue

`.claude-plugin/marketplace.json` is generated by `scripts/build-catalogue.sh` and CI fails on drift
(`--check`). Two modes:

- `legacy` (default, and what is committed today): `github` sources pointing at the old
  `albitor-plugin-<name>` repositories and tags, plus the retired `visual-*` entries. Existing
  consumers, including Albitor's pin audit, see exactly what they saw before.
- `monorepo`: one `git-subdir` source per plugin:

  ```json
  { "source": "git-subdir", "url": "albitor-ltd/albitor-plugins",
    "path": "plugins/auth", "ref": "auth/v0.7.0" }
  ```

  `git-subdir` takes `url`, `path`, `ref` and an optional full 40-character `sha`, and checks out
  only the subdirectory (Claude Code plugin marketplace reference). Albitor's pin audit joins
  entries on `repo`, which `git-subdir` entries do not have, so it must learn to read `url` and
  `path` before the switch-over.

### Switch-over (not done yet)

Do this only after every first-party plugin has been tagged `<name>/vX.Y.Z` from the monorepo and
Albitor's pin audit and tenant plugin sources understand `git-subdir`:

1. Push a tag `<name>/v<version>` for each plugin (the refs `--mode monorepo` emits).
2. Change the default of `mode` in `scripts/build-catalogue.sh` to `monorepo`, and the `--check`
   call in `.github/workflows/ci.yml` follows the default.
3. Run `scripts/build-catalogue.sh` and commit the regenerated `marketplace.json`.
4. Re-point tenant sources, then archive the old `albitor-plugin-*` repositories with a pointer
   README (keep their tags ingestible until the re-point is done).

## CI

Pull requests run: manifest validation (JSON parses, `name` equals the directory, semver
`version`, catalogue metadata present), catalogue reproducibility (`--check`), shellcheck and JSON
lint, and a placeholder `conformance` job reserved for the socket conformance and certification
harness (albitor-ltd/albitor#3164). Actions are pinned by full commit SHA.

## Third parties

Nothing here constrains anyone else. A plugin source may be a repository root, a subdirectory of a
repository, a git URL or an npm package, so third parties publish one repository per plugin or their
own monorepo. The platform runs the same conformance and certification harness at ingest that this
repository's CI runs earlier.

## Air-gapped / offline use

Internet-connected installs use the command above. Air-gapped or regulated deployments are handled
per engagement: clone this repository, assemble a local marketplace (relative-path sources) or load
via `claude --plugin-dir plugins/<name>`, and sign as required.
