# How-to guides (goal-oriented)

A how-to guide is a **recipe**: directions that take a *competent* user through the
steps to accomplish a specific real-world goal. It serves someone already at work
who knows what they want to achieve and needs to get it done.

Position on the compass: **action + application**. Practical (steps) in service of
*work* (applying existing skill to a task).

## Tutorial vs how-to (the distinction people get wrong)

They look similar — both are sequences of steps — but they serve opposite needs:

| | Tutorial | How-to guide |
| --- | --- | --- |
| Serves | learning | a task |
| Reader | a beginner | a competent user |
| Owns the goal | the author (teaching) | the reader (their real problem) |
| Path | one fixed, known-good path | adapts to the reader's situation |
| Success measured by | the learner gained skill | the goal was accomplished |

A tutorial is a lesson; a how-to is help getting a job done. Don't turn a how-to into
a lesson.

## What a good how-to does

- **Addresses a specific goal or problem**, named in the title: "How to …". The title
  is a real-world task the user recognises.
- **Assumes competence.** The reader knows the basics; you don't teach them, you
  direct them.
- **Focuses on the goal, omits the incidental.** Leave out anything not needed to get
  there. No conceptual detours.
- **Is a series of actions**, in a sensible order, that gets to the result.
- **Handles real-world messiness.** Unlike a tutorial's single clean path, a how-to
  can and should acknowledge branches ("if you're on Windows…", "if X is already
  configured, skip to…"), because real tasks vary.
- **Is practical, not complete.** It covers the sensible path to *this* goal, not
  every option (that's reference).

## What a how-to must NOT do

- Don't teach concepts — link to explanation instead.
- Don't try to be a comprehensive description of the machinery — link to reference.
- Don't wander off the goal. Everything serves getting the task done.
- Don't start from a beginner's zero — that's a tutorial.

## Writing checklist

- [ ] Title it as a goal: **"How to <achieve X>"**.
- [ ] Open by stating what the guide achieves and any assumptions/prerequisites.
- [ ] Give a clear sequence of actionable steps; use the imperative ("Run…", "Set…").
- [ ] Describe results and choices at decision points; let the reader adapt.
- [ ] Name the flags/keys used, but link to **reference** for their full definition.
- [ ] Link to **explanation** for the "why" rather than teaching it inline.
- [ ] Stop when the goal is met — no victory-lap theory.

## Naming a set of how-tos

Good how-to titles form a task index a user can scan: "How to deploy to production",
"How to rotate credentials", "How to add a new environment". If a title reads like a
lesson ("Understanding deployments") it belongs in explanation, not here.
